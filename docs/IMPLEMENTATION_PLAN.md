# Indexly 架构实施计划

本文依据 [整体架构设计](./ARCHITECTURE.md)，按可验证的产品增量安排工作。所有阶段均为待实施，本次仅新增设计文档。

## 1. 阶段与退出条件

| 阶段 | 主要交付 | 退出条件 |
| --- | --- | --- |
| P0 工程基础 | npm workspaces、TypeScript 核心包、契约模块、ESLint、格式化、CI、环境配置 schema、PostgreSQL 本地开发说明 | 全新安装可运行 lint/typecheck/test/build；现有算法用例迁移；用户未提交内容保留 |
| P1 身份与数据基础 | Better Auth、工作区/成员/邀请、项目/域名验证、Prisma 迁移、作用域 repository、审计、幂等/Outbox 与最小验证 Worker | 两个团队交叉访问全部被拒绝；最后一个 OWNER 受保护；未验证项目不能触发抓取；验证任务重试和挑战轮换正确 |
| P2 可靠抓取 | pg-boss Worker、安全 HTTP、robots/sitemap、frontier、页面提取、租约/fencing、限流/预算、取消和恢复 | 可对受控站点完成真实抓取；安全矩阵通过；Worker 被杀后恢复；重复任务不产生重复观测 |
| P3 报告闭环 | 可比基线、字段级有效性、事件、问题状态、发布事务、Summary、真实仪表盘及详情 | 三次抓取演示“基线 → 变化 → 解决”；部分/失败/取消不推进基线；页面不再依赖模拟数据 |
| P4 团队首版发布 | 每周调度、配额运维界面、公平性压测、完整导航/移动交互、查询性能、监控、备份恢复、历史清理 | 定时触发防重；容量与恢复目标实测；关键 E2E 和跨租户测试通过；上线配置齐全 |
| P5 后续增强 | 邮件摘要、Webhook、链接图/断链溯源、公开 API token、渲染抓取等独立需求；健康分 v1 已按 ARCHITECTURE.md §9 先行实现 | 每项单独确定语义、资源预算和验收；不作为首版已有能力展示 |

P0 → P1 → P2 → P3 → P4 是首版主依赖链。P1 数据契约稳定后，P2 抓取与 P3 的纯规则/UI 可并行；P3 的完整验收依赖 P2。认证验证邮件及最小验证消费者属于 P1，抓取报告邮件属于 P5。抓取基础配额与消费者释放策略在 P2 完成，P4 负责生产规模验证。

不估算未经容量、人员和部署环境验证的日历工期。每阶段结束交付可演示结果及验证记录，后续阶段继续沿用已确定的接口和语义。

## 2. 推荐的代码变更批次

1. 补工程配置和共享契约，迁移核心 `.mjs`，独立修正 URL 身份与地址分类，保留有效测试并添加已复现缺陷的回归。
2. 建立数据库迁移与租户 repository；加入身份、成员、邀请与权限。迁移中明确部分唯一索引、组合外键和锁顺序。
3. 实现项目策略版本与 DNS 验证；创建抓取 API 在同一事务写 Run、幂等记录、审计和 Outbox。
4. 打通 Outbox → pg-boss → Worker → Run 状态，先验证重复投递、失效恢复与取消，再接入公网访问。
5. 实现 SafeHttpClient 和模拟 DNS/网络适配器；安全测试通过后添加 robots、sitemap、解析、frontier 和预算。
6. 实现冻结观测、可比基线、事件、问题转换和原子发布，验证指标口径及规则版本变化。
7. 逐步把仪表盘、历史、页面详情和问题列表接入授权查询；补错误态、部分抓取态和移动端交互。
8. 加入调度、清理、运维与备份流程，执行生产规模样本测试和首版端到端验收。
9. 新增 `@seo/health-score` 纯规则包：发布事务内计算健康分并写入 CrawlSummary，overview API 与仪表盘展示；覆盖率不足时降级为原因与覆盖率展示，不给出分数。

每批次围绕一个可独立审查的行为，不同时引入数据库、队列、抓取和全部 UI 的大规模重写。

## 3. 必需的测试矩阵

| 层次 | 重点场景 | 工具/环境 |
| --- | --- | --- |
| 纯函数 | `/a` 与 `/a/`、重复查询参数、相对链接 base、robots 指令、canonical 候选、三值规则、首次基线 | Node test runner 或统一后的 TypeScript 测试执行器 |
| 安全 HTTP | 合法 fc/fd 域名、私网 IPv4/IPv6、mapped 地址、尾点主机、混合 DNS、rebinding、重定向、TLS、代理、正文解压超限 | 可注入 DNS/连接器、受控测试服务器；生产实现不能开放任意内网开关 |
| 数据与租户 | 组合外键、作用域读取、角色撤销、最后 OWNER、邀请码重复消费、跨租户游标和详情请求 | 临时 PostgreSQL 实例及真实迁移 |
| 并发与恢复 | 跨项目幂等键、双调度器、Outbox 标记前崩溃、租约被接管、陈旧 Worker 写入、取消与发布竞态、两个工作区竞争消费者 | 两个 Worker 进程、故障注入、真实 pg-boss |
| 抓取完整性 | 网络失败、429、404、robots 拒绝、非 HTML、解析失败、预算耗尽、已知 URL 不再被链接 | 受控站点图与固定响应 fixture |
| 报告与问题 | 基线/第二次变更/第三次修复、UNKNOWN 不解决、新 URL 的异常、策略重置、忽略与重新出现 | 纯规则测试 + 发布事务集成测试 |
| UI E2E | 登录邀请、切换工作区、启动抓取、轮询、取消、失败重试、筛选分页、移动导航、可访问名称 | Playwright，在测试环境连接真实 Web/Worker/DB |
| 运维 | 迁移兼容、优雅停机、数据库中断、超过 20 次抓取后的基线/Issue 引用清理、备份恢复、配额与查询延迟 | 预发布环境，记录原始测量结果 |

测试不依赖真实第三方网站的稳定性。联网安全边界测试使用受控适配器，少量真实公网冒烟仅在明确配置的验证站点运行。

## 4. 首版验收演示

准备一个拥有可验证域名的受控网站，至少包含正常 HTML、无标题页、重定向页、robots 禁止页和 sitemap。

1. OWNER 创建工作区并邀请 MEMBER、VIEWER；另一工作区成员访问项目应被拒绝。
2. 创建项目并验证 DNS；完成第一次抓取，界面显示已建立基线和可确认的当前问题。
3. 修改一个页面为 404、一个页面为 noindex、一个标题；第二次抓取显示对应事件、不同受影响页面数和问题证据。
4. 恢复上述问题，第三次抓取出现正确的已解决转换；标题再次修改只产生变化，不额外创建待解决问题。
5. 故意制造超时或降低页面预算，确认部分结果可检查，但基线与问题没有错误推进。
6. 在抓取中终止 Worker 并重启，再执行取消/重复触发测试，确认无重复报告且任务可收敛到终态。
7. 演示每周任务槽位防重、失效调度跳过、监控告警、历史清理和一次备份恢复。

## 5. 设计决策与后续变化

| 已确定的决定 | 重新评估的触发条件 |
| --- | --- |
| Next.js + 独立 Worker | Web 与任务需要不同运行环境时，保留契约拆部署 |
| PostgreSQL + pg-boss + Outbox | 队列与业务查询资源竞争经测量持续影响目标 |
| 每项目一个精确 hostname | 产品明确需要 www/多子域项目时，增加域名授权与跨主机调度设计 |
| HTTP 抓取 | 客户页面主要依赖 JavaScript，且能接受渲染资源成本 |
| PARTIAL 不发布正式变更 | 用户需要部分结果告警时，先设计逐字段基线和去重，避免误解决 |
| 健康分 v1（已实现，见 ARCHITECTURE.md §9） | 权重、饱和率、覆盖门槛或聚合语义需要调整时，递增 scoreVersion，历史分数保留原解释 |
| 应用层租户隔离 + 数据约束 | 安全或规模需求要求数据库级防线时加入并验证 RLS |

部署服务商、认证邮件服务商和具体依赖补丁版本在对应阶段选定。若容量、角色模型或范围发生变化，先更新架构文档和受影响的验收条件，再实现变更。
